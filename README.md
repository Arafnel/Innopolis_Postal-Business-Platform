## Как сдавать работы через GitHub

ЛР-2, ЛР-3 и ЛР-4 сдаются только через GitHub. **ЛР-1 можно сдать в Moodle или через GitHub** — порядок для неё описан [в условии ЛР-1](labs/lab-1/README.md#как-сдать).

### Где

У каждого из вас будет **один приватный репозиторий на весь курс** в организации курса `[ЗАПОЛНИТЬ: имя организации на GitHub]`. Доступ к нему есть у вас и у преподавателя. Работы лежат в нём каталогами `lr1/` (если ЛР-1 сдаётся через GitHub), `lr2/`, `lr3/`, `lr4/`.

Что нужно заранее:

1. **Аккаунт на GitHub с двухфакторной аутентификацией.** Нужен к занятию 10 (26.10), а тем, кто сдаёт ЛР-1 через GitHub, — `[ЗАПОЛНИТЬ: дата, не позже 21.10]`. Для второго фактора понадобится телефон или другое устройство.
2. **Имя аккаунта** сообщите преподавателю `[ЗАПОЛНИТЬ: куда и до какой даты]`. После этого вы получите приглашение в свой репозиторий.

### Рабочий цикл

1. **Одна ветка на работу:** `lr1` (при сдаче ЛР-1 через GitHub), `lr2`, `lr3`, `lr4`, каждая от `main`. В `main` попадает только принятое.
2. **В день выдачи откройте запрос на слияние (pull request) в режиме черновика (draft).**
   Заголовок: `ЛР-2 Архитектура и данные — Фамилия`. С этого момента преподаватель видит работу и может оставлять замечания к конкретным строкам.
3. **Коммит после каждого практикума**, а не один перед сдачей. Пример сообщения: `З-6: машина состояний, точка невозврата`.
   Число коммитов не оценивается. Оценивается то, насколько история связана с ходом курса: пять коммитов с понятными сообщениями лучше двадцати коммитов «правки».
4. **Сдача** — до начала занятия в день сдачи переведите запрос из черновика в состояние «Ready for review» и назначьте преподавателя рецензентом.
5. **После сдачи в ветку ничего не добавляйте.** Если работу вернут на доработку, правки идут отдельными коммитами в тот же запрос.
6. **Принятую работу преподаватель сливает в `main`.** Слияние означает приёмку.

### Как фиксируется срок

В момент дедлайна преподаватель записывает **хеш (SHA) последнего коммита** в ветке. Если историю переписать после дедлайна, этого хеша в ветке не окажется, и это будет видно.

**Опоздание.** Работа, сданная позже начала занятия, проверяется, но балл по критерию «Оформление» снижается. Для допуска к экзамену важно, что работа сдана, а не что она сдана вовремя.

**Если GitHub недоступен в день сдачи,** выложите работу архивом в Moodle и укажите хеш последнего коммита. Это считается сдачей в срок.

### Оформление в репозитории

- `README.md` каждой работы — это оглавление по пунктам задания со ссылками на файлы. Любой пункт должен находиться по оглавлению за один переход.
- **Схемы делайте в Mermaid прямо в `.md`.** GitHub отрисует их в браузере, а изменения в схеме будут видны построчно. Картинкой схему можно сдать только если нотация иначе не позволяет, и тогда рядом нужно положить исходник.
- Код должен запускаться по инструкции `RUN.md` без восстановления окружения по догадкам.
- **Артефакт практикума сразу кладите в тот каталог, где он станет частью работы.** Тогда к выдаче работы каталог уже наполовину заполнен.

Артефакт, который невозможно проверить из-за оформления, получает 0 баллов по критерию «Оформление».

## Критерии оценивания каждой работы

15 баллов = 3 критерия по 5 баллов.

| Критерий | 5 баллов | 3 балла | 1 балл | 0 баллов |
|---|---|---|---|---|
| **Корректность** | Решение технически верно, учтены граничные случаи и сценарии отказа | Решение в целом верно, граничные случаи не рассмотрены | Существенные логические ошибки | Решение неверно или не сдано |
| **Обоснованность** | Приведены инженерные аргументы выбора, рассмотрены альтернативы | Аргументы приведены, альтернативы не рассмотрены | Аргументация формальна | Обоснование отсутствует |
| **Оформление** | Артефакт читаем, соответствует нотации, самодостаточен, сдан через систему контроля версий | Незначительные отступления от нотации | Артефакт трудночитаем | Оформление не позволяет проверить работу |

Как критерии читаются для конкретной работы, сказано в её условии.

## Правило обращения с количественными данными

Курс построен на материале действующей промышленной системы, и на числа о ней правообладатель наложил ограничение. Правило распространяется и на ваши работы.

Правило действует в ЛР-2, ЛР-3 и ЛР-4. **В ЛР-1 правило применяется в той редакции, которая приведена в её условии.**

Каждое число в работе относится **ровно к одному из пяти статусов**, и от статуса зависит, как его записывать:

| Статус | Форма записи |
|---|---|
| Открытая отчётность организации | цифрами, со ссылкой |
| Внутренняя оценка для целей курса | **словами, без цифр** |
| Соотношение из внутренней продуктовой отчётности | цифрами с пометкой, без абсолютных значений |
| Учебное допущение | цифрами с пометкой «допущение» |
| Внешний проверяемый источник | цифрами, со ссылкой |

**Запрещено** приводить данные вне открытой отчётности, в том числе показатели чистой прибыли, а также детализацию по коротким периодам (по месяцам и неделям). Любая численная оценка приводится **вместе со списком допущений**, на которых она держится.

Для целей этого правила **содержимое вашего репозитория считается открытым документом**, хотя репозиторий приватный.

Это правило проверяется и на экзамене: вопрос 14 устного собеседования звучит так: «какие количественные данные вы использовали и на каком основании считаете допустимым их приведение в открытом документе».
