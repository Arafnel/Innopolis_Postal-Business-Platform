## Задание

Спроектируйте публичный программный интерфейс вашей сквозной фичи.

### (а) Три ключевые операции — ПК-2

Опишите **три ключевые операции** фичи в спецификации OpenAPI. Для каждой укажите:

- метод и путь;
- параметры, тело запроса и тело ответа;
- коды ошибок;
- стратегию версионирования;
- как обеспечена идемпотентность;
- **как проверяется, что объект принадлежит клиенту**, от имени которого пришёл запрос.

### (б) Пользовательская документация — ПК-2

Подготовьте фрагмент документации к интерфейсу. Его должно хватать, чтобы **внешний разработчик смог выполнить интеграцию** без устных пояснений.

### (в) Размыкатель цепи на Python — ПК-2

Реализуйте **размыкатель цепи (circuit breaker)** для одного вызова смежного сервиса — **в полном варианте, включая полуоткрытое состояние с пробным запросом**.

Покажите прогоном поведение в трёх ситуациях:

1. последовательные отказы смежного сервиса;
2. неудачный пробный запрос;
3. восстановление сервиса.

Укажите, **какую ошибку получает клиент, пока цепь разомкнута, и чем она отличается от обычного отказа смежной системы.**

### (г) Ролевая модель и матрица прав — УК-1, ПК-2

Опишите ролевую модель **с учётом того, что у одного клиента много пользователей**. Постройте матрицу прав **в трёх измерениях: субъект, операция, область видимости**. Для каждой операции укажите множество объектов, над которыми она разрешена. Обоснуйте выбор модели контроля доступа.

## Из чего собирается работа

| Пункт | Практикум | Что добавляется в работе |
|---|---|---|
| (а) | З-10 | одна операция → три; проверка принадлежности объекта клиенту |
| (б) | З-10; перечень внешних систем — З-13 | черновик → фрагмент, достаточный внешнему интегратору |
| (в) | З-11 | двухсостоянийный вариант → полный, с полуоткрытым состоянием |
| (г) | З-12 | матрица в трёх измерениях с областью видимости |

Операции должны опираться на решения ЛР-2: состояния, которые меняет операция, берите из вашей машины состояний, а смежный сервис для размыкателя — с вашей архитектурной схемы.

## Рекомендуемая структура каталога

```
lr3/
  README.md              оглавление по пунктам (а)…(г) со ссылками на файлы
  openapi.yaml           три операции: версионирование, идемпотентность,
                         модель ошибок, проверка принадлежности объекта
  docs/integration.md    документация для внешнего интегратора
  circuit_breaker/
    breaker.py           размыкатель цепи
    demo.py              прогон трёх ситуаций
    RUN.md               как запустить, вывод прогона, какую ошибку получает клиент
    requirements.txt
  g-access-model.md      ролевая модель и матрица прав
```

Спецификация должна проходить валидацию OpenAPI. Проверьте её любым валидатором, например в Swagger Editor. Код запускается командой из `RUN.md` на чистом окружении Python.

## Критерии оценивания — 15 баллов

Общая шкала курса (см. [README репозитория](../../README.md#критерии-оценивания-каждой-работы)). На что смотрим в ЛР-3:

- **Корректность:** повторный запрос с тем же ключом идемпотентности не создаёт дубля; размыкатель действительно проходит все три состояния, и прогон это показывает; матрица не позволяет пользователю одного клиента увидеть объекты другого.
- **Обоснованность:** стратегия версионирования и модель контроля доступа сопоставлены с альтернативами.
- **Оформление:** спецификация валидна, код запускается по `RUN.md`, документация читается без автора.

Действует правило о пяти статусах числа (см. [README](../../README.md#правило-обращения-с-количественными-данными)).

## Взаимное рецензирование на занятии 19

**Сданная ЛР-3 рецензируется другим студентом** на занятии 19 (30.11). Сразу после сдачи преподаватель назначит пары. Отдельный доступ не нужен: работа рецензента лежит в `submissions/<логин>/lr3/` этого же репозитория.

- **Предмет рецензии — только ЛР-3.** Рецензент видит и `lr2/` автора, но замечания даются к ЛР-3. Решения ЛР-2 можно привлекать как источник проблемы.
- **Одно замечание — одна задача (Issue)** в этом репозитории по шаблону «Замечание к ЛР-3». В заголовке — логин автора работы: `[ЛР-3][<логин-автора>] …`. Задача состоит из четырёх частей: что · почему это дефект (класс дефекта по каталогу занятия 19) · чем и кому грозит, со сценарием · альтернатива.
- Не меньше трёх замечаний, ранжированных **по последствию**: в шаблоне это поле «Последствие» (высокое / среднее / низкое). Хотя бы одно замечание должно быть из класса, не следующего из требований.
- До первого замечания рецензент задаёт одно уточняющее (тот же шаблон, тип «Уточняющий вопрос»).
- Автор отвечает **письменно в каждой задаче** одним из трёх способов и закрывает задачу итоговым комментарием. **Обоснованный отказ оценивается наравне с принятием; молчание или «учту» не принимаются.**

Рецензия оценивается в компоненте «Работа на занятиях», а не в баллах ЛР-3.
